# ZFP-0005: 提案机械校验与确定性修复

## 摘要

扩展 `proposal check` 的标题、草稿 marker 和定义锚点校验，并让 `check --fix`
从仓库已有的明确事实修复源文件。仓库继续通过 schema、模板与 `proposal.toml`
拥有规则，工具不猜测自然语言含义。

## 动机

现有修复只能重建索引，缺少固定 marker 或定义申报仍需手工处理。正文字符串扫描
还会把代码示例中的锚点当成定义。修复需要与校验共用 Markdown 解析结果，避免把
示例变成实际提案元数据。

## 设计

使用 Markdown 语法树识别标题、HTML 锚点和独立 blockquote marker；代码块、行内
代码与 HTML 注释不提供定义或 marker 事实。标题必须是非空单行文本，正文只能有
一个 H1，仍按现有元数据标题模式匹配。模板中的必需 H2 不得重复。配置的 marker
必须恰好出现一次且紧随草稿 H1。定义列表检查类型、ID 格式、重复项；真实定义
锚点检查格式、次数、申报与跨文档所有权。

`check` 保持只读。`check --fix` 先在内存中计算以下可确定的修复：

- 从有效的编号和标题生成缺失或不匹配的开头 H1；不从文件名猜元数据，也不删除
  正文中额外的 H1。
- 从配置补齐缺失的草稿 marker，或把唯一的独立 marker 移至 H1 后；重复或非独立
  marker 留给作者处理。
- 从规范且唯一的定义锚点补齐 `defines`，保留已有声明顺序。
- 对缺失锚点，只有一个正文 H2-H6 标题文本与 ID 完全相同时，才在该标题前补锚点。
  不通过翻译、slug 化或相似匹配推测定义位置。

候选源文件必须通过全部校验（包括显式要求的历史检查）后才写入，然后重建索引。
有无法修复的问题时不写文件，报告剩余诊断并说明候选修复未应用。不得删除未知
元数据、声明、重复锚点或正文来让检查通过。局部编辑保留 YAML 注释和无关格式；
不能安全编辑的 YAML 结构保持原样。再次执行修复应无变化。

## 兼容性

保留命令、退出码和只读 JSON 输出。修复调用的 summary 增加已修改源文件列表
`fixed_files`；未能应用候选修复时保持为空。规则收紧会揭示过去漏检的无效内容。
标签枚举、日期等仓库特有元数据仍由 JSON Schema 负责，不引入在线依赖或 GitHub
标签状态。`[defines]` 仍是可选策略。

## 验证

测试覆盖代码示例与真实结构的区分、不同围栏和 HTML 注释、空白及多行标题、重复
标题与 marker、非法定义 ID、所有权冲突，以及缺失 marker/申报/锚点的修复。
验证只读执行不写文件、歧义和历史失败不写文件、注释与换行保留、修复后索引一致、
二次修复幂等，并执行仓库完整检查。
