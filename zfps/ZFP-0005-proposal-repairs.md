# ZFP-0005: 提案机械校验与确定性修复

## 摘要

扩展 `proposal check` 的标题、草稿 marker 和定义锚点校验，并让 `check --fix`
从仓库已有的明确事实修复源文件。仓库继续通过 schema、模板与 `proposal.toml`
拥有规则，工具不猜测自然语言含义。

## 动机

现有修复只能重建索引，缺少固定 marker 或定义申报仍需手工处理。正文字符串扫描
还会把代码示例中的锚点当成定义。修复需要与校验共用 Markdown 解析结果，避免把
示例变成实际提案元数据。

## 设计

使用 Markdown 语法树识别标题、HTML 锚点和独立 blockquote marker；代码块、行内
代码与 HTML 注释不提供定义或 marker 事实。标题必须是非空单行文本，正文只能有
一个 H1，仍按现有元数据标题模式匹配。模板中的必需 H2 不得重复。配置的 marker
必须恰好出现一次且紧随草稿 H1。定义列表检查类型、ID 格式、重复项；真实定义
锚点检查格式、次数、申报与跨文档所有权。

`check` 保持只读。`check --fix` 先在内存中计算以下可确定的修复：

- 从有效的编号和标题生成缺失或不匹配的开头 H1；不从文件名猜元数据，也不删除
  正文中额外的 H1。
- 从配置补齐缺失的草稿 marker，或把唯一的独立 marker 移至 H1 后；重复或非独立
  marker 留给作者处理。
- 从规范且唯一的定义锚点补齐 `defines`，保留已有声明顺序。
- 对缺失锚点，只有一个正文 H2-H6 标题文本与 ID 完全相同时，才在该标题前补锚点。
  不通过翻译、slug 化或相似匹配推测定义位置。

候选源文件必须通过全部校验（包括显式要求的历史检查）后才写入，然后重建索引。
有无法修复的问题时不写文件，报告剩余诊断并说明候选修复未应用。不得删除未知
元数据、声明、重复锚点或正文来让检查通过。局部编辑保留 YAML 注释和无关格式；
不能安全编辑的 YAML 结构保持原样。再次执行修复应无变化。

### 完整校验与修复边界

配置必须拒绝输入输出路径冲突、字段角色冲突、错误类型、不可识别的索引字段与
不一致的状态表。文档发现不得静默漏掉嵌套或大写扩展名的 Markdown；不支持的
布局显式报错。Schema 引用只从仓库本地解析，无法解析的引用、未知格式和非 JSON
元数据均返回结构化错误。历史检查以 Git 根目录解析路径。

普通 HTML ID 必须唯一；本地链接检查文件和显式片段。自动生成的标题片段默认
不猜测，可在 `[links]` 中明确选择 `heading_ids = "github"`；`check = false`
可关闭本地链接检查。`[sections]` 可配置 `nonempty`、`ordered`、`no_skip_levels`
及 `placeholders`，分别约束必需章节正文、顺序、标题层级和独立占位文本。
`graph.acyclic_fields` 独立配置无环关系；requires 与 supersedes 角色自带无环检查。
草稿也检查已填写的关系引用，历史替代链追踪唯一现行所有者。

修复规则包括 `number`、`title`、`h1`、`marker`、`defines`、`deduplicate`、
`references`、`aliases` 与 `sections`。编号只能从无冲突的规范文件名恢复，标题
只能从与编号一致的唯一开头 H1 恢复。已有标题可清理首尾空白与冗余编号前缀。
空 defines 字段只有 Schema 要求且正文没有定义锚点时才补齐。重复声明与关系项
可去重；正文重复定义不自动删除。`[fix.aliases.<field>]` 声明字符串值的明确映射，
`fix.reference_style` 可选 `preserve`、`number`、`identifier`。章节修复只补模板
标题，不生成正文，空章节检查仍然生效。

`--diff` 只预览补丁，`--select` 选择修复规则，`--partial` 显式允许应用不会新增
关系、身份、Schema 或历史错误的源文件修复；默认仍要求候选整体合法。部分修复
后只要还有错误就返回失败且不更新索引。诊断始终描述实际文件状态，候选错误、
规则、依据、补丁与待修复项单独报告。写回在任何替换前准备全部临时文件，并校验
输入快照；普通 I/O 失败尝试回滚，报告写入或回滚失败的准确文件清单，不承诺跨
文件系统崩溃事务。

### 仓库作者规范与提案门槛

本次仓库配套完善 ZFP-0000 中的作者身份和提案判断说明。ZFP 的 `authors` 使用
小写 GitHub 用户名，具体格式由本仓库 schema 校验；不得通过自动修复猜测显示
名称与账号的对应关系。这不是通用 `zendev-proposal` 对所有仓库的强制策略。

是否需要提案取决于是否引入新的公共契约或治理决定，以及已有提案是否覆盖它。
实现已记录的决定无需重复提案；新增兼容接口仍属于新的公共契约。判断标准和
实例以 ZFP-0000 为准，贡献入口只提供导航，校验器不根据实现 diff 自动判定。

## 兼容性

保留命令、退出码和只读 JSON 输出。修复调用的 summary 增加已修改源文件列表
`fixed_files`；未能应用候选修复时保持为空。规则收紧会揭示过去漏检的无效内容。
标签枚举、日期等仓库特有元数据仍由 JSON Schema 负责，不引入在线依赖或 GitHub
标签状态。`[defines]` 仍是可选策略。

## 验证

测试覆盖代码示例与真实结构的区分、不同围栏和 HTML 注释、空白及多行标题、重复
标题与 marker、非法定义 ID、所有权冲突，以及缺失 marker/申报/锚点的修复。
验证只读执行不写文件、歧义和历史失败不写文件、注释与换行保留、修复后索引一致、
二次修复幂等，并执行仓库完整检查。
